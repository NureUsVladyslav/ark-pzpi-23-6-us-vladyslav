2 ХІД РОБОТИ
2.1 Текстовий опис інженерних рішень
Програмна система для безпеки житлових приміщень буде реалізована як клієнт-серверна система з централізованою серверною частиною, клієнтськими застосунками та реляційною базою даних. Архітектурні рішення системи спрямовані на забезпечення модульності, масштабованості, надійності та можливості подальшого розширення функціоналу.
Серверна частина системи буде реалізована на платформі Node.js з використанням фреймворку Express та мови програмування TypeScript. Архітектура серверної частини матиме шарову структуру та складатиметься з рівня обробки HTTP-запитів, рівня бізнес-логіки та рівня доступу до даних. Такий підхід дозволить розділити відповідальність між компонентами системи та спростить її супровід і розвиток.
Взаємодія між серверною частиною та зовнішніми компонентами здійснюватиметься за допомогою REST API з використанням формату обміну даними JSON. Клієнтські застосунки використовуватимуть API для автентифікації користувачів, керування приміщеннями, налаштування датчиків, перегляду стану системи та отримання повідомлень про події безпеки. Імітація роботи датчиків здійснюватиметься за допомогою симулятора, який надсилатиме на сервер сигнали про спрацювання датчиків у вигляді бінарних значень.
Для забезпечення контролю доступу в системі буде реалізована автентифікація користувачів на основі токенів. Авторизація виконуватиметься відповідно до ролі користувача, яка зберігатиметься як атрибут облікового запису та визначатиме дозволені дії в системі.
Зберігання даних буде здійснюватися у реляційній базі даних PostgreSQL. Взаємодія з базою даних реалізовуватиметься за допомогою ORM TypeORM, що дозволить описувати структуру бази даних у вигляді об’єктних моделей та спростить виконання операцій з даними. Для керування змінами структури бази даних використовуватиметься механізм міграцій (migrations), який забезпечить версіонування схеми даних і можливість контрольованого застосування змін.
Розгортання серверної частини та бази даних буде виконуватися з використанням контейнеризації за допомогою Docker, що забезпечить ізольоване та відтворюване середовище виконання системи.
У системі передбачається використання таких основних моделей даних: користувач, приміщення, датчик, подія, тривога та повідомлення. Користувач представляє обліковий запис із визначеною роллю доступу та має можливість створювати й керувати одним або кількома приміщеннями. Приміщення є логічною одиницею, до якої прив’язуються датчики та визначається режим охорони.
Датчики будуть представлені у вигляді програмних сутностей, що імітують роботу реальних пристроїв. Передбачається використання двох типів датчиків: датчиків руху та датчиків відкриття дверей або вікон. Датчики передаватимуть на сервер бінарний стан, який відображає факт спрацювання.
Події формуватимуться на основі сигналів, отриманих від датчиків, та зберігатимуться в журналі подій. У разі спрацювання датчика при активному режимі охорони створюватиметься тривога, яка відображатиме факт потенційної загрози. На основі тривог формуватимуться повідомлення для користувачів системи.
Зв’язки між моделями даних забезпечуватимуть цілісність інформації та дозволятимуть відслідковувати взаємозв’язок між користувачами, приміщеннями, датчиками та подіями безпеки.

2.3 Фрагменти програмного коду
Нижче наведено фрагмент коду, який реалізує створення нової кімнати в системі та автоматичне призначення користувача, що ініціював створення, власником цієї кімнати. Серверна частина взаємодіє з базою даних за допомогою ORM TypeORM. Після створення запису в таблиці rooms додатково створюється запис у таблиці room_members, який фіксує зв’язок між кімнатою та користувачем з роллю OWNER.
static async createRoom(userId: string, body: CreateRoomBody): Promise<ServiceResult<RoomDto>> {
    const roomRepo = db.getRepository(Room);
    const memberRepo = db.getRepository(RoomMember);


    const room = roomRepo.create({
      name: body.name,
      isArmed: false,
    });


    await roomRepo.save(room);


    const member = memberRepo.create({
      roomId: room.id,
      userId,
      memberRole: RoomMemberRole.OWNER,
    });


    await memberRepo.save(member);


    return { ok: true, data: toRoomDto(room) };
  }
Розглянемо наступний фрагмент коду, що демонструє реалізацію рольової моделі доступу (RBAC) у системі безпеки житла. Перед додаванням нового учасника до кімнати сервер перевіряє, чи має поточний користувач необхідні права доступу. У системі реалізовано обмеження, згідно з яким лише користувачі з ролями OWNER або ADMIN можуть додавати нових учасників, при цьому ADMIN не має права призначати ролі адміністратора або власника.
const actor = await memberRepo.findOne({ where: { roomId, userId: actorUserId } });
    if (!actor) return { ok: false, status: 403, error: "Forbidden (not a room member)" };

Наведений нижче фрагмент коду ілюструє обробку HTTP-запиту від клієнта для оновлення даних кімнати. Сервер приймає запит, перевіряє наявність ідентифікатора користувача, виконує валідацію вхідних даних та передає керування до сервісного шару, де відбувається робота з базою даних. У відповідь клієнт отримує стандартизований JSON-об’єкт з результатом операції або повідомленням про помилку.
router.patch("/:id", async (req: UpdateRoomRequest, res) => {
  const userId = getUserId(req, res);
  if (!userId) return res.status(401).json({ ok: false, error: "Unauthorized" });


  const { error } = updateRoomSchema.validate(req.body);
  if (error) return res.status(400).json({ ok: false, error: error.message });


  const result = await RoomService.updateRoom(userId, req.params.id, req.body);
  if (!result.ok) return res.status(result.status).json({ ok: false, error: result.error });


  return res.json({ ok: true, data: result.data });
});


2.4 Графічні ілюстрації
2.4.1 UML діаграма
UML-діаграма прецедентів відображає основні сценарії взаємодії користувачів із серверною частиною програмної системи безпеки житла. На діаграмі показано ключові ролі системи: користувач, адміністратор та симулятор датчиків, а також їхні дії щодо керування охороною, приміщеннями, датчиками, тривогами та журналами подій. Серверна частина системи відповідає за обробку сигналів від датчиків, формування тривог, збереження подій у журналі та надсилання повідомлень користувачам. Також відображено функції адміністрування, зокрема керування користувачами та перегляд системних журналів. Діаграма дозволяє наочно проаналізувати функціональні можливості серверного API та взаємозв’язки між прецедентами використання.

2.4.2 ER діаграма
ER-діаграма даних відображає концептуальну модель бази даних програмної системи безпеки житла та визначає основні сутності, їх атрибути та зв’язки між ними.
Центральною сутністю системи є Room (приміщення), яке представляє окремий об’єкт житла, що перебуває під охороною. Для кожного приміщення зберігається його назва, стан охорони (isArmed) та дата створення. Одне приміщення може бути пов’язане з декількома користувачами.
Сутність User (користувач) описує зареєстрованих користувачів системи. Зв’язок між користувачами та приміщеннями реалізований через асоціативну сутність RoomMember, яка дозволяє реалізувати відношення «багато-до-багатьох» та зберігати роль користувача в межах конкретного приміщення (OWNER, ADMIN, USER, DEFAULT), а також момент додавання користувача до приміщення.
У кожному приміщенні можуть бути встановлені Sensor (датчики), які мають тип (датчик руху або відкриття), назву та стан активності. Датчики генерують SensorEvent (події датчиків), що фіксують факт спрацювання або його відсутність у певний момент часу.
Події датчиків можуть призводити до створення Alert (тривоги) у разі, якщо режим охорони приміщення активний. Тривога має статус (відкрита або закрита), час створення та час закриття. Для кожної тривоги система формує Notification (сповіщення), які надсилаються користувачам, пов’язаним з відповідним приміщенням.
Для фіксації дій користувачів у межах приміщення використовується сутність RoomActivityLog, яка зберігає інформацію про тип виконаної дії, час її виконання, додаткові деталі та ціль дії (користувач, датчик або тривога). Даний журнал дозволяє відстежувати такі події, як увімкнення або вимкнення охорони, додавання датчиків, керування користувачами та закриття тривог.

2.4.3 Діаграма структури БД
Структура бази даних програмної системи SecureSpace побудована на основі реляційної моделі та відображена на ER-діаграмі. Центральною сутністю є таблиця rooms, яка представляє житлові приміщення та пов’язана з іншими таблицями за допомогою зовнішніх ключів. Користувачі системи зберігаються в таблиці users, а їхній доступ до приміщень реалізований через проміжну таблицю room_members, що дозволяє підтримувати зв’язок типу «багато-до-багатьох» і розмежовувати ролі користувачів. Датчики (sensors) та події від них (sensor_events) прив’язані до конкретних приміщень, що забезпечує централізований облік подій безпеки. Для фіксації тривожних ситуацій використовується таблиця alerts, а інформування користувачів реалізується через таблицю notifications. Журнал дій користувачів у межах приміщень зберігається в таблиці room_activity_log, що забезпечує аудит і відстеження змін у системі.
Схема бази даних відповідає вимогам нормалізації до третьої нормальної форми. Дані знаходяться у першій нормальній формі, оскільки всі атрибути є атомарними, а кожна таблиця має первинний ключ. Друга нормальна форма забезпечується відсутністю часткових залежностей, оскільки всі неключові атрибути залежать від повного первинного ключа відповідної таблиці. Третя нормальна форма досягнута завдяки усуненню транзитивних залежностей та винесенню логічно різних сутностей у окремі таблиці, пов’язані між собою зовнішніми ключами. Такий підхід мінімізує дублювання даних, підвищує цілісність інформації та спрощує подальше масштабування системи.
