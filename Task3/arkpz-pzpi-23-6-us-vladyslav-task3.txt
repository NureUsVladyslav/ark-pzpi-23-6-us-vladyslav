2 ХІД РОБОТИ
2.1 Текстовий опис інженерних рішень
Адміністративний функціонал програмної системи реалізований на серверній стороні та ізольований від користувацьких сценаріїв. Доступ до адміністративних операцій обмежується за допомогою ролей користувачів і перевіряється на рівні middleware.
Для автентифікації та авторизації використовується механізм JWT. Після успішного входу сервер формує токен, який містить ідентифікатор користувача та його роль. Токен передається в заголовку Authorization кожного запиту та перевіряється сервером. Адміністративні ендпоінти доступні виключно для користувачів з роллю адміністратора, що забезпечує розмежування прав доступу без використання серверних сесій.
У межах адміністрування реалізовано керування користувачами. Адміністратор має можливість отримувати список користувачів і змінювати їхній статус. Блокування користувача реалізоване шляхом оновлення статусу облікового запису в базі даних. Заблокований користувач не може проходити автентифікацію та виконувати захищені запити до системи.
Резервне копіювання даних реалізоване в контейнеризованому середовищі Docker. Серверна частина виконується разом із базою даних у контейнерах, що дозволяє створювати резервні копії незалежно від операційної системи хоста. Адміністративний ендпоінт ініціює створення дампу бази даних і збереження його у виділений каталог. Це забезпечує можливість відновлення даних у разі збою без зупинки основного сервісу.
Захист персональних даних користувачів забезпечується на базовому рівні за рахунок централізованої серверної обробки, обмеження доступу до даних через механізми авторизації та відсутності прямого доступу клієнтів до бази даних. Передавання даних між компонентами системи здійснюється виключно через захищені API-запити, а критичні операції доступні лише автентифікованим користувачам з відповідними правами доступу.
Підтримка локалізації реалізована на рівні серверної логіки та клієнтських застосунків. Система передбачає можливість використання різних мовних налаштувань без зміни бізнес-логіки, що дозволяє розширювати кількість підтримуваних мов без впливу на адміністративний функціонал.
Усі адміністративні операції виконуються через захищені REST API ендпоінти.
2.2 Фрагменти програмного коду
У ході виконання роботи було реалізовано механізм автентифікації користувачів за допомогою JWT-токенів. Нижче наведено фрагмент коду middleware, який відповідає за перевірку токена доступу в HTTP-запитах:
const header = req.headers.authorization;


if (!header) return next();


if (!header.startsWith("Bearer ")) {
  return next(
    new AppError("AUTH_REQUIRED", 401, { reason: "INVALID_AUTH_HEADER" })
  );
}


const token = header.slice("Bearer ".length).trim();
if (!token) {
  return next(new AppError("AUTH_REQUIRED", 401, { reason: "MISSING_TOKEN" }));
}


try {
  const payload = jwt.verify(token, process.env.JWT_ACCESS_SECRET!) as JwtPayload;


  res.locals.user = {
    id: payload.sub,
    role: payload.role ?? "USER",
  } as any;


  return next();
} catch {
  return next(new AppError("AUTH_REQUIRED", 401, { reason: "TOKEN_INVALID" }));
}
Даний код призначений для автоматичної перевірки наявності та коректності JWT-токена у заголовку Authorization. Спочатку перевіряється сам факт наявності заголовка, після чого контролюється його формат відповідно до стандарту Bearer <token>. Це дозволяє відсіяти некоректні або пошкоджені запити ще до їх обробки бізнес-логікою. Після виділення токена виконується його криптографічна перевірка за допомогою секретного ключа JWT_ACCESS_SECRET. У разі успішної перевірки з токена витягується ідентифікатор користувача та його роль, які зберігаються у res.locals.user для подальшого використання в контролерах та сервісах. Такий підхід дозволяє централізовано реалізувати автентифікацію та мінімізувати дублювання коду в інших частинах системи.
Окрім механізмів входу в систему, у проєкті реалізовано функції адміністрування, зокрема створення резервних копій бази даних. Наступний фрагмент коду демонструє процес формування резервної копії PostgreSQL у Docker:
const backupsDir = path.resolve(process.cwd(), "backups");
fs.mkdirSync(backupsDir, { recursive: true });


const stamp = new Date().toISOString().replace(/[:.]/g, "-");
const fileName = `backup-${stamp}.sql`;
const filePath = path.join(backupsDir, fileName);


const { POSTGRES_DB, POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_CONTAINER } = process.env;


if (!POSTGRES_DB || !POSTGRES_USER || !POSTGRES_PASSWORD) {
  throw new AppError("BACKUP_FAILED", 500, { reason: "ENV_NOT_SET" });
}


const dump = spawn(
  "docker",
  ["exec", "-e", `PGPASSWORD=${POSTGRES_PASSWORD}`, POSTGRES_CONTAINER!, "pg_dump", "-U", POSTGRES_USER, POSTGRES_DB],
  { shell: true }
);


const out = fs.createWriteStream(filePath);
dump.stdout.pipe(out);


let errText = "";
dump.stderr.on("data", (d) => (errText += d.toString()));
dump.on("close", (code) => {
  if (code !== 0) {
    throw new AppError("BACKUP_FAILED", 500, { reason: "PG_DUMP_FAILED", code, stderr: errText });
  }
});
Цей фрагмент коду відповідає за автоматичне створення резервної копії бази даних у вигляді SQL-файлу. Спочатку створюється директорія backups, якщо вона відсутня, що гарантує коректне збереження файлів. Назва файлу формується на основі поточної дати та часу у форматі ISO, що дозволяє уникнути конфліктів і забезпечує зручну ідентифікацію резервних копій. Перед запуском процесу перевіряється наявність обов’язкових змінних середовища, які містять параметри підключення до бази даних. Сам дамп виконується за допомогою утиліти pg_dump, яка запускається всередині Docker-контейнера через spawn, що дозволяє коректно обробляти великі обсяги даних у потоковому режимі. Вивід команди перенаправляється безпосередньо у файл, а у випадку помилки формується детальне повідомлення з описом причини збою.
2.3 Графічні ілюстрації
Діаграма діяльності адміністрування відображає послідовність дій адміністратора та серверної частини під час виконання адміністративних операцій. Процес починається з автентифікації користувача та перевірки його ролі. Після успішної авторизації адміністратор обирає необхідну дію, а сервер перевіряє повноваження, обробляє запит і виконує відповідні операції з базою даних або сервісами резервного копіювання. За результатом виконання повертається статус операції, який відображається адміністратору.
  

Рисунок 2.1 - Діаграма діяльності
UML діаграма взаємодії блокування та розблокування користувача відображає послідовність дій між адміністратором, клієнтським інтерфейсом і серверною частиною під час зміни статусу облікового запису. Адміністратор ініціює операцію, після чого сервер перевіряє JWT-токен та права доступу.
У разі відсутності необхідних повноважень запит відхиляється з відповідним кодом помилки. Якщо перевірки пройдені успішно, виконується пошук користувача в базі даних і оновлення його статусу. Результат операції повертається клієнту та відображається адміністратору.
